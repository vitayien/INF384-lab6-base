> **Evidencias de GitHub Actions pendientes de proporcionar:** todos los runs del pipeline son locales al repositorio remoto de GitHub. Para completar las columnas *Run fallido* y *Run corregido*, ejecuta el pipeline (`git push` al branch `main` o crea un PR) y proporciona las URLs con el formato `https://github.com/<usuario>/<repositorio>/actions/runs/<run-id>`. Las evidencias locales verificadas (resultado de `npm test` y `npm audit`) están documentadas en las columnas de justificación.

## Cambios a la propuesta de Kiro

| Documento | Qué propuso Kiro | Qué se cambió | Por qué |
| --- | --- | --- | --- |
| `requirements.md` — AC-11 | Kiro definió `cycle` como `(entero entre 5 y 10)` sin contemplar valores nulos | Se amplió a `(entero entre 5 y 10 para cursos obligatorios, null para cursos electivos)` | La inspección de `data/cursos.json` confirmó que todos los 54 cursos electivos tienen `"cycle": null`. Restringir `cycle` a enteros habría generado una inconsistencia entre el requisito y el modelo de datos real del repositorio y el steering (`product.md`) |
| `src/routes/habilitados.js` — validación de Content-Type (AC-5) | Kiro generó `if (req.is('application/json') !== 'application/json')`, comparando el valor de retorno con la cadena literal | Se simplificó a `if (!req.is('application/json'))` | `req.is()` devuelve la cadena coincidente (truthy) si hay match o `false`/`null` (falsy) si no; la negación directa es semánticamente equivalente, más idiomática en JavaScript y elimina la comparación redundante con la cadena literal |
| `package.json` + `jest.config.js` — gate de cobertura (AC-13) | Kiro configuró `npm test` como `jest` (sin `--coverage`) y no incluyó `coverageThreshold` en `jest.config.js`; la cobertura era verificable manualmente pero no bloqueaba el CI | Se actualizó `npm test` a `jest --coverage` y se añadió `coverageThreshold: { global: { lines: 80 } }` en `jest.config.js` | El requisito AC-13 exige cobertura ≥ 80 % verificable en CI. Sin el umbral configurado, una regresión que redujera la cobertura por debajo del mínimo no bloquearía el pipeline automáticamente; con el umbral, Jest devuelve exit 1 y el job `build` falla |
| `package.json` — versión de `lodash` | Kiro no gestionó la versión de `lodash`; el proyecto base usaba `4.17.20`. La instrucción pedía actualizar a `4.17.21` | Se actualizó a `4.18.1` en lugar de `4.17.21` | El advisory HIGH de lodash afecta al rango `4.0.0 - 4.17.23`: `4.17.21` sigue siendo vulnerable (lo confirma `npm audit --audit-level=high` con exit 1). La primera versión limpia es `4.18.1` (recomendada por `npm audit fix`). Actualizar a `4.17.21` habría bloqueado el gate SCA sin resolver la vulnerabilidad |
